# ラン結果の可視化は「参加マトリクス」を主役に据え、標準ライブラリだけで書く

<!-- shunk031/tsubame-agentsociety2#5 の設計メモ。実装: scripts/plot_run.py / tests/make_run_fixture.py -->

いま知りたいのは「プールが枯れたか」ではなく「そもそも誰が動いたか」である。
shunk031/tsubame-agentsociety2#2 が示すとおり、4 エージェント 4 ラウンドで提出は毎回 1〜2 件しかない。
この状態でプール推移だけを眺めても、そこに映るのは実装の不備であって、エージェントの戦略ではない。
だからレポートの一枚目は、誰がどのラウンドで実際に採取したかを並べた行列にする。

生成機構は Python 標準ライブラリのみ、出力はインライン SVG と CSS の単一 HTML。
プロトタイプの実測で 26 KiB・0.1 秒、外部参照ゼロ。plotly を inline で埋め込む案（1 ファイル約 4.9 MB）とは 190 倍の差がつく。

このメモで決めたいのは次の 3 点。

1. パネル構成をこの順序・この取捨で確定してよいか
2. 生成機構を標準ライブラリのみとし、`plotly` / `pandas` / `duckdb` を使わない方針でよいか
3. `scripts/check_replay.py` とレポートで、参加率を数えるロジックを共有するか、各自で持つか

## 論じる範囲

対象は `CommonsTragedyEnv` のラン 1 件以上を入力とし、単一 HTML を出力するスクリプト 1 本。
ラン間比較は最初から設計に含める（shunk031/tsubame-agentsociety2#5 が明示的に求めている）。

対象外は 3 つ。ジョブ投入や取得の自動化は `scripts/sync.sh` 側の担当として切り離す。
`SimpleSocialSpace` への対応は、環境ごとに指標が違うので共有地の悲劇が固まってから。
LLM 呼び出し単位の応答時間は、`sim.log` に残るのがステップ境界だけなので測れない。ラウンド単位の実時間で代替する。

## データの実像 — 仕様と実装がずれている 3 点

agentsociety2 2.8.7 のソースを読んで確かめた。shunk031/tsubame-agentsociety2#5 の「Available data」表と食い違う箇所がある。

**JSON 列は JSON 文字列として書かれる。** `storage/replay_sink.py:65` の `_normalize` が `dict` / `list` を `json.dumps` で文字列化する。
`last_round` も `profile` も、`json.loads` を 2 回通さないと中身に届かない。
DuckDB の `read_json_auto` で読んでも VARCHAR のまま返るので、上流の `replay_reader.py` を真似ても事情は変わらない。

**`submitted_agents` と `pending_extractions` は常に空。** `contrib/env/commons_tragedy.py:346` がラウンド実行直後に両方を `clear()` し、そのあとで行を書き出す。
つまり参加の記録は `last_round.extractions` のキー集合にしかない。提出しなかったエージェントは 0 ではなく不在として現れる。
shunk031/tsubame-agentsociety2#5 の表が `pending_extractions` を参加の出どころに挙げているのは、この点で誤り。

**`last_round` は前ラウンドの要約を再掲する。** 誰も提出しなかったステップでは `round_history[-1]` がそのまま書かれ、`round_number` も据え置かれる。
`round` 番号で重複排除しないと、成立しなかったラウンドを成立したものとして数えてしまう。

失敗の帰属は `agent/base/agent.py:1700` の `Agent 3: ReAct tool failed: action=think observation=...` から取る。
ログ形式は `[%(asctime)s] %(levelname)-7s %(message)s`、ステップ境界は `Running n/m steps with tick=` と `Running questionnaire round_N`。

### sim.log の実物には 2 つの罠がある

実機ラン sim-8645779 に当てて分かった。合成フィクスチャだけでは出なかった。

**Ray ワーカーの出力が混ざる。** sim.log はジョブの標準出力そのものなので、ワーカーの行は
`\x1b[36m(step_agent_batch pid=2116)\x1b[0m [時刻] WARNING Agent 4: ...` の形で届く。
色コードとプレフィックスを剥がしてから読む必要がある。
`^\[` に錨を下ろした素朴な読み方では、このランの ReAct 失敗 15 件のうち 4 件しか拾えなかった。残り 11 件はすべてワーカー側にある。
ついでに、プレフィックスの `step_agent_batch` / `questionnaire_agent_batch` はそのまま「run 中の失敗か questionnaire 中の失敗か」を教えてくれる。

**タイムスタンプのない行は順序が信用できない。** `[EnvActor] ask instruction='...' took 6.24s` と
helper のプラン実行トレースには時刻がなく、Ray がまとめてフラッシュするため、時刻付きの行との相対位置が実際の発生順とずれる。
実際 sim-8645779 では、ラウンド 1 のトレースがラウンド 3 の境界より後ろに現れ、
helper 自身の `Task: It is now round N` ブロックの内側にも、別のラウンドの結果が紛れ込んでいた。
そこでラウンドの割り当ては、行に埋め込まれたシミュレーション時刻 `[Thursday, 2026-01-01 09:15:00]` から
`(時刻 - start_t) / tick + 1` で計算する。シミュレーション時刻は 1 ラウンドにつき 1 tick ずつ進むので、これだけが決定的に効く。
`ask_env` の所要時間はラウンド別に出さず、分布として出す。

### shunk031/tsubame-agentsociety2#6 のステップ構成変更に追随する

作業中に、shunk031/tsubame-agentsociety2#6 が `ask` と `intervene` を丸ごと廃止し、1 ラウンド = `run` + `questionnaire` にしていることが分かった（その後マージ済み）。
影響は 3 つあり、すべて対応済み。

`artifacts/intervene_step_*.md` が生成されなくなるので、指示文は `init_config.json` の `personality` から取る。
新しい構成では、ゲームのルールと行動指示は全エージェント共通の profile 前半（`Your disposition:` より前）に入っている。

ラウンド境界を名乗るログ行が `Running questionnaire round_N` だけになる。これは `run` ステップの**後**に出るので、
フェーズに分割してから後ろ向きにラウンド番号を埋め、questionnaire が付かない末尾の run だけ前向きに補う。
これで旧構成（`Intervening: It is now round 3` がある）と新構成の両方が同じ結果になる。

`steps.yaml` のラウンド数も `intervene` の個数では数えられない。`questionnaire_id` の `round_N` を主、`intervene` と `run` の個数を従にした。

両構成のフィクスチャ（`tests/make_run_fixture.py --layout run-only | ask-intervene`）で、失敗のラウンド別集計が一致することを確認した。

## パネル構成 — 上から 7 枚

冒頭に判定バンドを置く。参加率・成立ラウンド数・プール残量・ReAct 失敗件数の 4 つを大きく出し、
参加率 75% 未満なら「参加が薄い」、40% 未満なら「シナリオを検証できていない」と文言で断じる。
`check_replay.py` が `exit 0` で見落とす「動いたが何も起きていないラン」を、開いて 2 秒で判別させるのが狙い。

**1. 参加マトリクス（行=エージェント、列=ラウンド）。**
セルは採取量、斜線は提出なし、灰色はラウンド自体が不成立。
右端に提出回数と累計ペイオフ、下端にラウンドごとの提出数とプール残量を置く。
shunk031/tsubame-agentsociety2#5 の「per-agent extraction heatmap」と「participation rate」を 1 枚に統合したのは意図的で、
両者は同じ行列の縦読みと横読みにすぎない。2 枚に割ると、読者は 1 つの問いに答えるために 2 つの図を往復することになる。
行見出しには性格（disposition）を添える。

**1b. その採取は本当にそのエージェントのものか。** 参加マトリクスの直下に置く。マトリクスの数字すべてに条件を付けるものだから、離すと意味がない。
3 つを見る。`ask` / `intervene` ステップが存在するか（存在すれば helper が環境に到達できるので、どの採取も本人のものだと断定できない）。
ログから helper の提出だと特定できた行。`last_round.extractions` のキーのうち `core_agent_profile` に無い名前。
該当するマトリクスのセルには `*` と赤い破線を付ける。

実機ランでは、ラウンド 1 と 2 の `Agent-1: 5` が helper の提出だと特定できた。Agent-1 は一度も提出していない。
名前の照合のほうは 0 件だった。この照合が捉えられるのは `Agent 3` のような書き損じだけで、実在する名前を騙った提出は素通りする——
実機で起きたのは後者なので、照合だけに頼ると「異常なし」と表示してしまう。だから helper の存在そのものを先に出す。

**2. 参加率の推移。** ラウンドごとの提出割合。ラン間比較の主役はこの図で、shunk031/tsubame-agentsociety2#2 の効果測定はここだけを見れば足りる。

**3. プールの減り方。** 実測の残量に加えて、全員が毎ラウンド上限まで採取した場合の下限を網かけで重ねる。
この 2 本の隙間が「このランがシナリオをどれだけ動かせていないか」そのものになる。不成立ラウンドには縦線を立てる。

**4. 累積ペイオフ。** エージェントごとの折れ線。多く採った者が最後に得をしたか、という shunk031/tsubame-agentsociety2#5 の問い 3 に答える。

**5. 申告と実測。** questionnaire の自己申告と replay の実測を並べた表。
shunk031/tsubame-agentsociety2#5 は散布図を提案しているが、表にした。点数が十数個しかない散布図は、いちばん重要なセル——
提出していないのに数値を申告したセル——を他の点に埋もれさせてしまう。表なら赤 1 色で名指しできる。
なお、プール枯渇で比例配分が起きたラウンドでは、申告（要求量）と実測（配分量）が正当にずれる。
`pool_after == 0` かつ配分合計が `pool_before` に一致することを条件に検出し、食い違いには数えない。

1 回の上限が 10 なのに `20` や `98` と答えたセルは、別枠で数える。実機ランでは 16 セル中 6 件がこれだった。
採取量の記憶違いではなく質問に答えていない回答なので、自己申告の精度を測る材料に混ぜると精度を過小評価する。

**6. 動かなかった理由。** `sim.log` の ReAct 失敗を、エージェント別・原因別（存在しないツール／読み取り専用ステップでの行動／引数不一致／応答が空）に集計する。
参加率が低いとき、原因がモデル能力か指示文かツール定義かを切り分ける材料になる。該当ログ行は `<details>` に畳む。

**7. ラウンド所要時間と ask_env の往復。** ステップ境界から測ったラウンド別の実時間の棒グラフに、
`ask_env` 往復時間の分布（件数・合計・中央値・最大）と遅い順の上位を添える。
実機ランでは往復 34 回・合計 181 秒・中央値 3.9 秒・最大 25.1 秒で、エージェント 1 体あたりの待ち時間はここが支配していた。
エージェント数を増やす判断の入力になる。

末尾の付録に、エージェント一覧と各ラウンドの指示文を畳んで置く。
指示文を埋め込むのは、参加率がランの間で変わったとき最初に疑うのが文言だからで、
残すべきはそのランで実際に使われた文言になる。`gen_config.py` は書き換わるので、現在の実装を見ても過去のランの条件は分からない。

### 落としたもの

**性格別の平均採取量（shunk031/tsubame-agentsociety2#5 の問い 6）は図にしない。**
`gen_config.py` は 6 種類の性格を 4 エージェントに割り当てるので、1 群あたり最大 1 サンプルになる。
観測 1 個の平均を棒グラフにすれば、統計に見える何かを提示することになる。
代わりに性格を参加マトリクスの行見出しに書き、比較は読者の目に委ねる。1 群 3 エージェント以上になった時点で図にする価値が出る。

**エージェントの自然文の推論は本文に載せない。** questionnaire の `reason` はセルの tooltip に入れる。
走査するための文書に散文を流し込むと、走査できなくなる。

## 生成機構 — 標準ライブラリのみ

`plotly` / `pandas` / `duckdb` は `agentsociety2` の依存として `uv.lock` に確かに入っている（plotly 7.0.0、pandas 3.0.5、duckdb 1.5.5）。
shunk031/tsubame-agentsociety2#5 の「No new dependencies」は事実として正しい。それでも使わない。軸を 4 つ置いて比較する。

| 軸           | 標準ライブラリ + インライン SVG                                    | plotly を inline 埋め込み                                |
| ------------ | ------------------------------------------------------------------ | -------------------------------------------------------- |
| 出力サイズ   | 26 KiB（実測）                                                     | 約 4.9 MB / ファイル（plotly.min.js 4,851,164 バイト）   |
| 実行場所     | Python 3.9 以上ならどこでも。手元の MacBook でもログインノードでも | `uv sync` 済みの共有領域の環境が要る                     |
| 依存の性質   | なし                                                               | `agentsociety2` の推移的依存に自前スクリプトがぶら下がる |
| 図以外の要素 | 表・ログ抜粋・指示文を同じ枠組みで書ける                           | figure は生成できるが、HTML の残り 7 割は結局手書き      |

決め手は 2 つある。

第一に、レポートの中身の大半は図ではない。参加マトリクス、申告と実測の表、失敗の集計、ログ抜粋、指示文——
これらに plotly は何も貢献しない。折れ線 3 本と棒グラフ 1 枚のために 4.9 MB を積む取引になる。
しかも扱うデータは 4×4 の 16 セルで、`<rect>` と `<polyline>` を並べれば済む規模でしかない。

第二に、README「依存構成の制約」が示すとおり、この環境は protobuf の上限と vLLM の下限が拮抗していて、依存を 1 つ足すのが高くつく。
推移的依存に頼るのは、依存を宣言しないまま依存することであり、`agentsociety2` が次に上がったときに黙って壊れる。
標準ライブラリだけなら、ログインノードで `uv` を通さず素の `python3` で叩ける。
共有ファイルシステム上の重い環境を起こさずに済むのは、TSUBAME では実務上の利点になる。

インタラクティブ性を失う点は認める。ただし hover と zoom は、16 セルの表に対しては装飾に近い。
tooltip は `<title>` 要素でまかない、JavaScript は 1 行も使っていない。
配色は CSS 変数で定義し、`prefers-color-scheme` でライト・ダークの両方に対応させた（両モードでスクリーンショット確認済み）。

## 実装と検証

- `scripts/plot_run.py` — 生成本体。`python3 scripts/plot_run.py <run_dir> [<run_dir> ...] -o report.html`、`--label` でラン名を指定
- `tests/make_run_fixture.py` — 合成ランの生成。`--scenario bad` が shunk031/tsubame-agentsociety2#2 の再現（提出 1〜2 件、最終ラウンド不成立）、`--scenario good` が全員参加で比例配分まで起きるラン。`--layout` で新旧のステップ構成を切り替える（既定は現行の `run-only`）

**実機ラン sim-8645779 に対して動く。** 初回実行で 35 KiB / 0.1 秒。
参加率 25%（16 機会中 4 件）、成立 3/4 ラウンド、ReAct 失敗 15 件と出て、shunk031/tsubame-agentsociety2#2 の記述と一致した。
合成フィクスチャ 4 種（bad / good × 新旧レイアウト）でも動く。外部参照は `grep` で 0 件。
Python 3.9 の構文で解析可能、3.11 と 3.14 で実行確認済み。ヘッドレス Chrome でライト・ダーク両モードの描画を確認した。

実機に当てて初めて出た不具合が 2 つある。Ray プレフィックスで失敗の 73%（15 件中 11 件）を取りこぼしていたこと、
タイムスタンプのない行を位置でラウンドに割り当てていたこと。どちらも合成フィクスチャでは再現しなかった。
フィクスチャを実装に忠実に作っても、ジョブの標準出力がどう混ざるかまでは想像で補えない。

フィクスチャは実装に忠実に作った。`zlib.crc32` による 256 シャード分割、JSON 列の文字列化、
ラウンド不成立時の `last_round` 再掲、比例配分の端数処理（`_calculate_actual_extractions_sync` の移植）まで再現している。
これを書く過程で、追記専用シャードに同じランを 2 回書くとエージェントが倍に見えると分かったので、
`core_agent_profile` は id で重複排除した。`--resume` したランで同じことが起きうる。

## 未解決の論点と暫定スタンス

**`check_replay.py` は残し、レポートはその隣に置くべきだと考える。**
両者は役割が違う。`check_replay.py` はジョブの中で走り、終了コードで成否を返す門番であり、GPU を確保している最中に動く必要がある。
レポートはジョブの外で、人間が読むために生成する。門番に HTML を書かせるのは筋が悪い。

参加率の判定を `check_replay.py` に足す件は、shunk031/tsubame-agentsociety2#6 で**すでに実装されている**。
`MIN_PARTICIPATION`（既定 0.5）を環境変数で受け、`last_round` を `round` 番号で重複排除し、
`extractions` のキー集合を数える。プロトタイプで独立に書いたロジックと一致した。
別々に書いて同じ形になったのだから、この読み方は正しいと考えてよい。残る作業は、レポート側でこのロジックを再実装しない形にするかどうかだけ。
共有するなら `scripts/lib/` に小さな読み取りモジュールを置くことになるが、
関数 3 つの重複を避けるために `check_replay.py` の自己完結性（`python3 scripts/check_replay.py` 単体で動く）を捨てるのは割に合わないと考える。現状は各自で持つ。

**レポート生成をジョブの最後に自動で走らせるかは決めていない。** 現時点では走らせない側に傾いている。
`sim.log` はジョブが終わるまで完結しないし、レポートは GPU を使わない。
ログインノードで `scripts/plot_run.py runs/<id>` を叩くほうが、失敗しても再実行が安い。

**ラン間比較でエージェント数や性格構成が違う場合の扱いは未確定。**
現在の実装は参加率（割合）で正規化しているので条件が違っても重ねられるが、
累積ペイオフを重ねるのは意味が薄い。いまは比較時に参加率とプールだけを共有軸に載せ、
残りのパネルはラン別に積んでいる。この線引きでよいか、意見がほしい。
