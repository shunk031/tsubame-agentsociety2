# LLM エージェントを多数動かすための GPU 構成

TSUBAME 4.0 / H100 / Qwen3.6-27B / SocialMediaSpace / `agentsociety2` 2.8.7。

## 結論

- GPU 枚数の差は、この測り方では検出できない
  - 512 体 4 ラウンドを 6 回実行 → 所要は 27〜221 分
  - 4 枚: 27 / 152 / 221 分、8 枚: 27 / 96 / 187 分
  - ➜ 同一構成内のばらつきが、構成間の差を覆っている

- 毎時イベント数で正規化しても同じ
  - 4 枚: 311〜880 件/時、8 枚: 404〜1,136 件/時
  - ➜ 範囲が重なる。優劣を言えない

- ばらつきの原因は特定できていない
  - 時間切れの多さでは説明がつかない: 0 件で 187 分のランがある
  - イベント数も 396〜1,467 と 3 倍以上振れる
  - ➜ 同じ設定でも仕事量そのものが違う

- 先に必要なのは、ばらつきを抑える条件の特定
  - 構成の比較はその後

## 背景

- 多数の LLM エージェントで社会シミュレーションをしたい
  - 対象はエージェント個々の応答ではなく、エージェント間に生まれる相互作用
  - 相互作用は数がなければ発生しない: 数体では会話が閉じる
  - ➜ 100 体規模を動かせることが前提条件

- 100 体規模 × 10B 以上 → 計算資源の問題になる
  - 1 体が 1 回行動するたびに LLM を呼ぶ
  - 小さいモデルでは足りない: 相手のエージェント名を壊し、誰が誰に話したか分からなくなる
  - ➜ 10B 以上を 100 体ぶん、同時に回せる環境が要る

- TSUBAME 4.0 が使える ➜ H100 を多数確保できる
  - シナリオは [`SocialMediaSpace`](https://github.com/tsinghua-fib-lab/agentsociety/tree/main/packages/agentsociety2/agentsociety2/contrib/env/social_media)
    - `agentsociety2` に同梱の環境モジュール。SNS を模した場を提供する
    - エージェントは投稿・返信・いいね・フォロー・検索でやり取りする
    - 選定理由: ツールの多くが他エージェントの id を取る = 相互作用が発生する設計

- GPU を確保しても、リクエストが足りなければ使われない
  - 4 GPU に 128 体では、vLLM の待ち行列が常に空だった
  - ➜ 何体なら足りるかを調査。指標は毎時イベント数

## 手法

`agentsociety2` + `vLLM` の構成を採用した。

- [`agentsociety2`](https://github.com/tsinghua-fib-lab/agentsociety): エージェントで社会シミュレーションを行うフレームワーク
  - 清華大の研究グループが公開。社会科学の実験環境
  - エージェントは考えて行動を選び、その結果が場に反映される
  - 全員の行動が揃ってから、時間を 1 コマ進める

- [`vLLM`](https://github.com/vllm-project/vllm): LLM をサービングする推論エンジン
  - HTTP で推論を受け付ける
  - 多数のリクエストをまとめて処理し、終わったものから返す
  - 計算ノードから外部の API は呼べない。vLLM も同じジョブの中で自分で立てる

- 測るもの: 毎時イベント数
  - replay に記録された投稿・返信・フォローを数える
  - 所要時間はステップ 1 開始から最終アンケート開始まで
  - 電力は補助。`nvidia-smi` 5 秒間隔、定格 700W に対する比
    - 複数ノードでは片方のノードしか測れない

## 実験

実験はすべて Qwen3.6-27B と SocialMediaSpace で行い、4 ラウンド走らせて毎時イベント数を測る。
GPU 数・エージェント数・ノード数を変え、スループットがどう変わるかを調べる。

### 実験 1

- 128 体 / H100 4 枚
  - 同時に処理されるリクエストは 64 本前後
  - 待ち行列は常に空
  - ➜ エージェント数が処理能力に足りていない

### 実験 2

既定値のままでは数時間で応答が止まる。原因は 4 つ。いずれも共有 API を前提とした設定が、
自前で立てたサーバに合っていないことによる。

| 何が起きるか | 原因 | 変更 |
| --- | --- | --- |
| 数時間後に応答が止まり、復帰しない | クライアントが健全なサーバを不調と誤判定して遮断する | クールダウンを無効化 |
| 同時実行数が 268 から 130 へ勝手に下がる | 応答の遅さを混雑と誤読する機構が働く | 相対判定を無効化 |
| 128 体の半分以上が待たされる | 想定文脈長が実態の 8 倍で、同時に持てる数が 58 本に制限される | 65536 → 16384 |
| 5 分で 285 件が時間切れ | 待ち時間の上限が 60 秒。混雑時は正常な応答でも超える | 60 → 900 秒 |

- 1 つ目が最も重い
  - 時間切れが積もる → クライアントが唯一の接続先を「不調」と記録 → 送信を止める
  - 送り先が他にない → 復帰しない。サーバは空いたまま
  - 報告済みの挙動: [BerriAI/litellm#41223](https://github.com/BerriAI/litellm/issues/41223)
  - ➜ 呼び出し側が設定した時間切れを、サーバ側の障害として数えている

- 4 か所を直した後、126 分の実行で時間切れ 0 件

### 実験 3

- GPU を 1 枚に減らす
  - 電力: 64% → 81%
  - 毎時イベント: 333 → 124
  - ➜ 1 枚あたりの読み出し量が増えて電力計は上を向くが、こなせる仕事は減る
  - ➜ 電力は代理指標であり、目的ではない

### 実験 4

- 4 枚のまま 512 体に増やす
  - 同時に処理されるリクエスト: 64 本前後 → 394 本
  - 待ち行列ができる
  - ➜ 128 体では供給不足だった

### 実験 5

- 2 ノード 8 枚に広げる
  - 単一エンドポイントのまま。呼び出し側の改造は不要
  - 起動の順序依存が 4 つ。いずれも実機でのみ露見

| 症状 | 原因 |
| --- | --- |
| `Permission denied (publickey)` | 計算ノード間の `ssh` に鍵がない。`qrsh -inherit` を使う |
| 待機側が 5 分で終了 | 待機側を先に起動した。受付側が先 |
| 待機側がいつまでも起動しない | 待ち受けポートをループバックで監視していた |
| 受付側が準備完了を待ち続ける | 待機側のランク番号が受付側と衝突 |

## 結果

512 体 / 4 ラウンド / 各構成 3 回。

| GPU | 所要 | events | 毎時 | 時間切れ |
| --- | --- | --- | --- | --- |
| 4 | 27 分 | 396 | 880 | 0 |
| 4 | 152 分 | 789 | 311 | 60 |
| 4 | 221 分 | 1,423 | 386 | 99 |
| 8 | 27 分 | 511 | 1,136 | 1 |
| 8 | 96 分 | 647 | 404 | 9 |
| 8 | 187 分 | 1,467 | 471 | 0 |

- 範囲が重なる ➜ 構成差を検出できていない
- 時間切れでは説明がつかない ➜ 0 件で 187 分のランがある
- イベント数が 3 倍振れる ➜ 同じ設定でも仕事量が違う

## 再現手順

```
NUM_AGENTS=512
MODEL=Qwen/Qwen3.6-27B
MAX_MODEL_LEN=16384
MAX_NUM_SEQS=512
GPU_MEMORY_UTILIZATION=0.90
AGENTSOCIETY_LLM_REQUEST_TIMEOUT=900
AGENTSOCIETY_LLM_LATENCY_DEGRADE_FACTOR=inf
```

- `GPU_MEMORY_UTILIZATION` は 0.90 が上限
  - 0.95 にすると埋め込み用サーバが起動に失敗する
  - 生成用と埋め込み用で 1 枚を分け合うため、合計が 1.0 を超えられない
- クールダウンの無効化はライブラリ側の修正が要る
  - 上流の修正: [BerriAI/litellm#41230](https://github.com/BerriAI/litellm/pull/41230)

## 限界

- 各構成 3 回では、ばらつきの分布を決められない
- 所要時間はステップ 1 開始からの値。モデル読み込みを含まない
- 複数ノードでは片方のノードしか電力を測れていない
- ばらつきの原因は未特定。時間切れ説は反例がある
