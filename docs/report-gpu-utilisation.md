# 128 体の LLM エージェントで GPU を使い切る

TSUBAME 4.0 / H100 / Qwen3.6-27B / AgentSociety 2.8.7 / SocialMediaSpace。

未確定の節は空のまま置く。埋まっていない数値を推測で補わない。

## 概要

- 当初の目標「GPU 電力を常時 80% 以上」は未達・かつ指標として不適切と判明
  - 電力は上がっても毎時イベント数は増えず
  - 飽和させるほど待ち時間が伸び、タイムアウトから崩壊へ
  - ➜ 測るべきは毎時イベント数
- 4 件の障害を特定・修正
  - litellm が健全なバックエンドをクールダウンで遮断
  - 適応セマフォが応答時間のばらつきを輻輳と誤読
  - `max_model_len` が同時実行枠を制限
  - GPU メモリ配分の溢れで埋め込みサーバが起動失敗
- スループットは GPU 数とエージェント数の両方に依存
  - 128 体 / 4 GPU: 333 件/時
  - 512 体 / 4 GPU: 891 件/時
  - ➜ GPU を増やすだけでは足りない
- 複数ノード (2 ノード 8 GPU) が単一エンドポイントで動作

## 背景

- ティックは社会シミュレーションの単位であり、バリアはその要件
  - 同一ティック内で全エージェントが行動 → 全員が同じ時刻の世界を観測
  - バリアを外すと、あるエージェントが数ステップ先の世界を見ながら別のエージェントは過去を見る
  - ➜ 相互作用の記録として成立しない。バリアは守る前提
- 実装: ドライバがエージェント id を分割 → Ray Task を並列投入 → 全完了を待つ → env と時計を進める
  - 1 エージェント = 1 リクエストではない: ReAct の連鎖で逐次に複数回 LLM を呼ぶ
  - 連鎖の長さには個体差 → ティックの長さは最も長い個体が決める
  - 詳細: `docs/agentsociety2-behaviour.md`
- 計算資源から見ると、負荷はティック内で単調に減る
  - 開始直後: 全エージェントが連鎖の 1 本目を同時に投げる
  - 末尾: 連鎖の長い個体だけ残る
  - ➜ 問いは「バリアをどう外すか」ではなく「バリアを保ったまま GPU をどう埋めるか」
- 上流の既定値は共有リモート API を前提
  - 自前バックエンドを飽和させる運用と噛み合わない箇所が複数

## 手法

- 指標: 毎時イベント数 (replay の投稿・返信・フォロー)
  - 電力は代理指標として補助的に記録
  - 稼働時間はログ上の最初と最後のエージェント行動の間隔
- 比較軸: GPU 数 / エージェント数 / 並列方式 (TP vs. DP) / ノード数
- 計測: `nvidia-smi` 5 秒間隔・定格 700W に対する比
  - 制約: サンプラは head ノードのみ。複数ノードでは worker 側の GPU を測れない

## 実験

### 実験 1: 並列方式と GPU 数

- TP は per-GPU の計算密度と電力を下げる ([arXiv:2504.17674](https://arxiv.org/pdf/2504.17674))
- 同一ベンチ・並列度 32・Qwen3.6-27B

  | | GPU | ピーク電力 |
  | --- | --- | --- |
  | `bench-8688255` | 4 (TP) | 536W = 77% |
  | `bench-8688263` | 1 | 677W = 97% |

- ➜ 電力だけ見れば 1 GPU が有利。ただし後述の通り仕事量は逆

### 実験 2: 上流既定値の影響

| 既定値 | 症状 | 変更 |
| --- | --- | --- |
| `AGENTSOCIETY_LLM_LATENCY_DEGRADE_FACTOR=4.0` | `429=0` なのに並列度を 268 → 130 に自己削減 | `inf` |
| `max_model_len=65536` | 同時実行枠 58 本 (実プロンプトは 8K 台) | `16384` |
| `AGENTSOCIETY_LLM_REQUEST_TIMEOUT=60` | 5 分で 285 件のタイムアウト・電力 82% → 44% | `900` |
| litellm `Router` のクールダウン既定 | 1,187 件のタイムアウト後に 2 時間無音 | `disable_cooldowns=True` |

- クールダウン遮断の機序
  - 飽和運用では待ちが正常 → タイムアウトが出る
  - litellm が 408 として失敗数に計上 ([BerriAI/litellm#41223](https://github.com/BerriAI/litellm/issues/41223))
  - デプロイメントが 1 個・フォールバック無し → 遮断先が無い
  - ➜ 全リクエストが vLLM に届かないまま失敗・復帰しない

### 実験 3: エージェント数

- 4 GPU 固定でエージェント数を変える
- 128 体では `Waiting: 0` → 供給不足
- 512 体では `Running: 394` → 4 GPU を占有

### 実験 4: 複数ノード

- vLLM multi-node data parallel: head が HTTP・他ノードが `--headless` で RPC 参加
  - 単一エンドポイントのため呼び出し側の改造は不要
- 起動の順序依存が 4 つ (すべて実機でのみ露見)

  | 症状 | 原因 | 対処 |
  | --- | --- | --- |
  | `Permission denied (publickey)` | 計算ノード間 ssh に鍵が無い | `qrsh -inherit` |
  | worker が 5 分で `Shutting down` | worker 先行起動 | head 先行 |
  | `RPC port open` が出ない | ループバックを監視 | head 外部アドレスを監視 |
  | `Waiting for READY message` のまま | worker のランクが head と衝突 | `--data-parallel-start-rank` |

## 結果

### スループット

| 構成 | GPU | 体数 | 稼働 | events | 毎時 | timeout |
| --- | --- | --- | --- | --- | --- | --- |
| 修正前 | 4 (TP) | 128 | 65 分 | 489 | 449 | 1 |
| AIMD 絞り込み有効 | 4 (TP) | 128 | 141 分 | 330 | 140 | 3 |
| 1 GPU | 1 | 128 | 265 分 | 550 | 124 | 1,315 |
| 全修正 | 4 (TP) | 128 | 126 分 | 699 | 333 | 0 |
| 全修正 | 4 (DP) | 512 | 33 分 | 486 | 891 | 64 |
| 全修正・2 ノード | 8 (DP) | 512 | | | | |

### 安定性

- 全修正後の 128 体 / 4 GPU: 126 分を完走・タイムアウト 0 件
  - 修正前は 1〜1,315 件
- 5 時間の無言停止が再現しないかは未確認
  - 該当ランは 4 ラウンドを 2 時間 22 分で完走し、壁に到達せず

### 電力

| 構成 | 平均 | 80% 以上の時間 | 最低 |
| --- | --- | --- | --- |
| 4 GPU (TP) | 63〜64% | 28〜35% | 10% |
| 1 GPU | 81% (崩壊前) | | 21% |

- ➜ 目標「常時 80% 以上」はどの構成でも未達

### 複数ノード

- 2 ノード 8 GPU・512 体が単一エンドポイントで稼働
- 毎時イベント数は未確定

## 残課題

- `check_replay.py` が `SocialMediaSpace` を誤判定
  - `social_media_agent_state` を書いているのに「env state が無い」と報告
  - ➜ 当該シナリオのランは必ず失敗扱いになる
- GPU サンプラが head ノードのみ
  - 複数ノードの電力を測れない
- 末尾の谷を縮める手が未検証
  - 連鎖の長さの個体差がティックの長さを決める
  - 生成長の上限は連鎖の回数を減らさないため効果薄
  - ➜ ReAct の最大ターン数が候補。ただしエージェントの思考を切ることになるため、
    シミュレーションの妥当性と引き換えになる
- テンプレートキャッシュのヒット数は依然 0
  - 実測の指示文間類似度は最大 0.6760 (既定閾値 0.85)
