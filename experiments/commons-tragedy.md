# 共有地の悲劇

## テーマ

有限の共有資源を前に、エージェントが自制するか奪い合うか。

## 設定

| 項目                 | 値                                 |
| -------------------- | ---------------------------------- |
| 環境モジュール       | `CommonsTragedyEnv`                |
| エージェント数       | 4                                  |
| 資源プール           | 100（補充されない）                |
| 1 ラウンドの採取上限 | 1 人あたり 10                      |
| ラウンド数           | 4                                  |
| 1 ラウンドの模擬時間 | 900 秒                             |
| モデル               | `Qwen/Qwen3.5-4B`（thinking 有効） |

- 採取した 1 単位が 1 点
- 全員の要求がプール残量を超えたら、要求量に比例して配分
- エージェントには性格を割り当てる（慎重・競争的・分析的・衝動的など）

## 手順

```
run            エージェントが観察し、採取量を決めて提出する
questionnaire  いくら要求したかを答えさせる
run
questionnaire
...            4 ラウンド繰り返す
```

- ルールも採取の作法もプロファイルに書いてある
  - `run` ステップに外から届くものは何もない。プロファイルと自動の観察と記憶だけ
  - プロファイルは毎ターン読まれる唯一のテキスト
- 採取が起きるのは `run`
  - `run` は全エージェントの `step()` を必ず呼ぶ → 参加は 1 体ずつ独立した話になる
- `questionnaire` が測定器。`run` だけでは記録がほとんど残らない
- `ask` と `intervene` は使わない
  - エージェントに届かず、上流のヘルパが代わりに動いてしまう
  - 前回の run では、そのヘルパが `Agent-1` を名乗って自分で採取を提出していた
  - README の落とし穴を参照

## 見るもの

| 指標                 | 出どころ                             |
| -------------------- | ------------------------------------ |
| ラウンドが成立したか | `round_number`                       |
| 何人が参加したか     | `last_round.extractions` のキー数    |
| プールの減り方       | `current_pool_resources`             |
| 誰がいくら採ったか   | `pending_extractions` / `last_round` |
| 本人の申告する方針   | `artifacts/questionnaire_*.json`     |

ラウンドは 1 体が提出した時点で成立する。`round_number` が伸びていても、
動いているのが 1 体だけなら共有地の話にはならない。
参加人数を先に見る。`scripts/check_replay.py` が出す。

## 実測（`Qwen/Qwen3.5-4B` / 4 エージェント / 4 ラウンド）

```
round 1: 3/4  Agent-1: 4, Agent-2: 4, Agent-3: 8
round 2: 4/4  Agent-1: 5, Agent-2: 1, Agent-3: 10, Agent-4: 10
round 3: 4/4  Agent-1: 4, Agent-2: 3, Agent-3: 10, Agent-4: 10
round 4: 2/4  Agent-2: 1, Agent-3: 10
```

- プール 100 → 20。4 ラウンドで 8 割が消えた
- Agent-3 は残量に関係なく上限の 10 を取り続けた
- Agent-2 は残りが減るほど 4 → 1 → 3 → 1 と抑えた
- ➜ 性格の違いは採取量に出ている。ただし n=1 なので、傾向として読む段階ではない
